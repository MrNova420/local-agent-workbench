# Session Continuity and Run Recovery Implementation

**Status:** source implementation in progress; verification intentionally queued.  
**Applies to:** Electron workbench plus its pinned shared Python engine.  
**Settings:** selected context, maximum output, and model-default reasoning are not changed.

**Current paired engine source:** `a9360935fd1bb733d23ce35273bfe50798e23cce` (unpublished; regressions intentionally queued).

## Implemented in this source batch

- A session-owned task checkpoint now carries the original goal, user follow-up instructions, captured runtime settings, plan, completed operation references, changed files, verification, and the latest assistant update. Complete transcript, emitted reasoning, and complete tool results remain in session history/activity.
- The engine injects that checkpoint on each inference request, including after complete-turn compaction. Compaction records the omitted and retained turn counts and checkpoint inclusion/estimated size. The checkpoint supplements history; it does not replace the configured context or output cap.
- When a new task starts, the immediately preceding archived task's outcome, plan, blockers, decisions, changed files, and verification are also summarized into the checkpoint request. Complete task history remains saved; the model receives this prior summary only alongside the active task checkpoint.
- Legacy flat checkpoints are migrated into the current task shape. Completed, cancelled, failed, and stopped tasks are retained in task history when a later task starts.
- Ollama prompt_eval_cached_count is now retained by the shared runtime adapter. Usage events are stored with turn, model/provider, and run settings.
- Sidecar plan updates already used the durable activity stream. The renderer now also updates the visible Plan section from those same activity events; it no longer waits for a separate ephemeral plan event.
- Run event deltas are coalesced and appended to per-session JSONL journals in both app and project stores. Streamed text/reasoning and command output flush at intervals; operation, plan, compaction, usage, and terminal boundaries flush immediately. A journal cursor lets session recovery replay only events newer than its last snapshot. Duplicate app/project journal records use shared event IDs.
- Each journal event now tracks which mirror durably accepted it. A failed project or app append is retried only to the missing mirror; already-saved stream chunks are no longer mutated by coalescing, and a session cursor advances only for events present in both mirrors. Session listings replay the selected/consistent journal so active/interrupted status is current.
- Full JSON snapshots are now written at important boundaries and at a slower interval during streaming, instead of once per second. Temporary Windows PermissionError replace failures receive bounded exponential retry. The save result reports app and project success independently; the UI no longer claims the app copy succeeded when it did not.
- Recovery replays post-snapshot partial text, reasoning, plan updates, operation start/output/result, generation usage, and terminal state. Text already received before a provider error is retained in the transcript. Malformed or unreadable journal records are surfaced in the Activity Trace and a warning; original journal bytes are preserved. Interrupted writes remain uncertain and are never automatically retried.
- Before a follow-up inference request clears the previous request's streaming buffer, its completed assistant text and reasoning are copied into the recoverable message checkpoint. Terminal replay also updates the task checkpoint status and blocker/verification fields.
- Terminal workflow outcomes are stored separately from run completion: discussion, plan-only, blocked, changed, inspected, command-completed, and command-failed. The renderer labels these from host-observed actions; it does not equate command completion with passing tests. A new task clears the previous task's visible plan, while active follow-ups keep it.
- The sidecar now forwards the engine's successful terminal outcome to the renderer only after session persistence, matching cancellation/error ordering. A missing successful terminal event is saved as a failure with a checkpoint blocker rather than silently labeled discussion; queued worker and persistence checks cover event ordering and fail-closed recovery.
- Task intent is now explicit (`auto`, `discuss`, `plan`, `implement`) and persisted per session and per turn. Build requests in Automatic mode plus explicit Plan/Implement tasks get a host-created checklist before inference; the model refines that same plan through `update_plan`. Discussion/Plan and Read-only access expose only read tools and suppress MCP tools for that turn; selected access/approval and model settings remain independent. This code is unverified.
- Terminal verification now carries an evidence contract in both the run state and task checkpoint: whether a requested implementation changed the project, whether changed files were inspected afterward, and the results of approved commands. A command exit of zero is not represented as a passing test. The engine requests an inspection when changes exist but none has been recorded; if an implementation request still returns without a host-observed change, the outcome is `implementation_incomplete` instead of discussion. Explicit Implement under Read-only access is reported as blocked. This code is unverified.
- The outcome card restores that evidence from the session snapshot and shows it after relaunch. A completed command cannot hide a missing post-change inspection; the renderer warns from the inspection contract and displays the exact persisted evidence summary. Queued renderer coverage also keeps older records readable without inventing evidence. Source-only, UI acceptance still pending.
- Every actual provider request now emits a compact prompt-provenance record into the same mirrored activity journal. It reports request message roles/sizes, context/output budget, checkpoint and compaction inclusion, project instruction and retrieved-file paths, exact tool/MCP names, enabled/available/catalog-included skills, and skill results retained in that request. Prompt text and credentials are not duplicated. Source-only, restoration/UI acceptance pending.
- Each request card now also records the provider/API path, selected model and API model ID, exact runtime options, requested/effective context when reported, output limit, reasoning override presence, keep-alive, and a clearly labeled estimated input count. Provider-returned prompt, cached-prompt, generated-token, and timing counters are linked to that request and restored through journal replay. Older records and unavailable metrics are labeled as unrecorded; no values are inferred or used to alter a request. Mocked runtime, sidecar, persistence-replay, and renderer regressions are queued, not run.
- Request execution now records and restores prepared, dispatched/header-wait, response-header/status, stream-ended, failed, and cancelled states. The live chat phase distinguishes the response-header wait from first-token/prefill wait; the local request socket can be cancelled during either wait without unloading the model. The stream and model response have no deadline after connection establishment. Delayed-header and phase-rendering checks remain queued.
- The plan tool now accepts optional task-specific acceptance criteria. The engine carries them through compaction checkpoints; the sidecar stores them in the plan activity journal; session restoration reads the latest plan snapshot; and the Plan panel presents criteria separately from checklist progress. A new task's explicit empty snapshot prevents stale criteria from a previous task resurfacing. Source-only, regression coverage queued.
- An active task that grows beyond the inference input budget can now compact at complete assistant/tool exchange boundaries inside that same user turn. It keeps the task prompt and newest complete exchanges that fit, persists the omitted-group count, and points the model to saved operation IDs. The new read-only `read_operation_result` tool retrieves full saved output or requested character ranges from the captured session; its lookup cannot cross into another session. This preserves the configured context/output settings and canonical history. Regression and visible continuation checks remain queued.
- ToolRegistry now initializes its plan state before the first inference request; review found the engine accessed the field before the first model `update_plan` call could create it. A queued regression covers the initial empty state.
- Streamed tool-call preparation now creates a durable activity row using only provider/tool identity and argument size. Repeated token fragments update the same turn/request/call row; complete batches transition it to assembled and provider errors transition it to interrupted. Journal recovery upserts the row, while partial arguments remain absent. Worker, persistence, and renderer regressions are queued.
- When the saved checkpoint itself becomes large, compaction now creates a separate budgeted inference view. It retains the full disk checkpoint, active goal/plan/settings, recent follow-ups and operation references; every summarized category is counted and exposed through the same persisted context activity row. Context/output/reasoning selections are not adjusted. Regressions are queued.
- Approved commands stopped after launch or terminated by timeout are now marked `uncertain` because partial file effects may already exist. Their possible effects trigger workspace inspection; the renderer warns before the user treats the result as a clean cancel or definite failure. A queued regression distinguishes these from cancellation before launch.
- The active-task checkpoint explicitly instructs the model to inspect the saved operation result and workspace before requesting or repeating an uncertain operation; uncertain operations are never automatically replayed. The continuity regression is queued.
- `read_operation_result` now falls back to the engine's in-memory completed-operation map when running without the desktop's durable session callback, so standalone CLI use does not advertise an unavailable lookup. In the desktop, the captured session store remains authoritative, with engine memory as same-run fallback. Regression queued, not run.
- Long chat/trace activity histories now render progressively: the latest 100 records appear first, with explicit loading of earlier records in batches. All records stay in persisted state; this is not a retention cap. Regression and visible scroll/restore acceptance are queued.
- Resource display now distinguishes Agent Workbench sidecar metrics, Ollama/llama.cpp worker CPU/RAM, NVIDIA worker-process VRAM when available, and device-wide GPU utilization/power. This does not claim selected-model utilization. Mocked coverage and live hardware acceptance are queued.
- Approved command tools no longer default to 120 seconds or cap explicit timeouts at one hour. The model is instructed to omit `timeout_seconds` for long builds/checks, leaving user cancellation available; explicit positive task-specific timeouts remain possible. Regression and visible long-command acceptance are queued.
- The retained CLI approval dialog now presents exact argv/PowerShell text and truthful timeout semantics. CLI approval and cancellation acceptance remain queued.
- Mocked resource-attribution coverage is owned by the engine repository alongside `telemetry.py`; it remains queued and unrun.
- The required cancel chooser now waits for explicit sidecar acknowledgment; a failed IPC call leaves it open, and a no-longer-active run is reported instead of silently looking canceled. Finish-after-current-operation receives the same acceptance check. Mocked and visible chooser tests remain queued.
- App-close choices also wait for host acknowledgment. Cancel-and-close validates cancellation acceptance and waits for run-idle before shutdown; failures keep the modal available instead of silently closing.
- The active chat supports a durable follow-up queue: prompts can be drafted during inference without changing the active request, are saved in both session mirrors, remain project-bound, and start only after explicit user selection. Queue removal is persisted with the selected prompt's new run snapshot to avoid automatic replay. No queue-size or prompt-length cap is added.
- Large generated files can now be constructed across model responses with `write_file` followed by ordered `append_file` chunks. Appends use an atomic replacement assembled with streaming file copies, require the existing project file, honor the same access/approval/path rules, and become durable changed-file evidence. This preserves the selected per-request output cap without imposing a file-size ceiling; runtime acceptance remains queued.
- Approval mode now includes a saved-chat-session grant: the first action opens the ordinary exact-action dialog; choosing “Approve this session” saves the grant to both mirrors before the action is released. Matching explicit deny/ask policies retain precedence, and changing away from this mode clears the stored grant. The UX and mirror-failure paths remain unverified.
- Prompt cache reporting now distinguishes full, partial, and missing provider counters. A missing cached-token field is no longer counted as zero; the worksheet also surfaces llama.cpp current-slot cached prompt tokens when reported by `/slots` and labels prompt evaluation time separately from cache hits. Actual KV allocation/precision stays unavailable unless a runtime reports it. Model Library featured picks are derived from exact installed tags and display the locally observed quantization metadata; all other installed models and Hugging Face search remain available.
- Updater source uses the Electron public release feed for packaged Windows x64 Squirrel installs, downloads in the background while idle, and waits for an explicit restart/install click. The beta.2-to-beta.3 installed upgrade and workspace recovery canary remains pending; no new release is being published in this work.
